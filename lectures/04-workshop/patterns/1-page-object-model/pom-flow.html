  • 1. A page object is a class: one per page, created with new
  • 2. The constructor stores page and builds the locators as fields on this
  • 3. Methods are shared by all objects and use this.* to reach the right fields
  • 4. No assertions inside: tests assert on public readonly locators
What is a Page Object? The basics in 2 minutes click or press I to show / hide

1. The idea in one sentence

A Page Object is a class that represents one page (or one component). It keeps the page's locators inside and offers methods named after what a user does: login(), addTask().

Analogy: a TV remote. You press "volume up" (a method); the wires (selectors) stay hidden inside the box.

2. Anatomy of a page object

export class LoginPage {
  private readonly usernameInput: Locator; // hidden
  readonly errorMessage: Locator;          // for assertions

  constructor(private readonly page: Page) {
    this.usernameInput = page.locator('#username');
    this.errorMessage = page.locator('#login-error');
  }

  async login(user: string, pass: string) {
    await this.usernameInput.fill(user); // ...
  }
}

3. new, constructor and this

CodeWhat happens
new LoginPage(page)creates an empty object, runs the constructor with this = that object, returns it
constructor(private readonly page: Page)TypeScript shortcut: stores the argument as this.page
this.usernameInput = ...a field: data stored on this object
loginPage.login(...)runs the shared method with this = loginPage (the object before the dot)
const { login } = loginPage; login(...)no object before the dot, so this = undefined and you get a TypeError

4. When is a page object created?

  • Once per test, in beforeEach (folder 1) or inside a fixture (folder 5).
  • Each test gets a new page, so it needs new objects. Never keep a page object in a module-level variable shared by tests.
  • Creating it does nothing in the browser. Locators are lazy; they are only looked up when an action or expect uses them.

5. What goes in, what stays out

  • In: locators, user actions, navigation, public locators that tests assert on.
  • Out: expect(...) assertions: they belong in the test.
  • Out: test data: pass it as arguments.
  • Out: setup like API login or seeding data: that is a job for fixtures.

6. Where page objects are used in real projects

NeedPage object example
Big formscheckoutPage.fillShipping(address) hides 10 fields behind one method
Reusable componentsclass Header, class DataTable, used inside pages: this.header = new Header(page) (composition)
Multi-step flowsa method returns the next page: const dashboard = await loginPage.submit() → DashboardPage
Large teamsa shared vocabulary: everyone writes cartPage.removeItem(...), nobody copies selectors

7. Why use page objects?

  • One place to fix: rename a button and change one file, not 30 tests.
  • Readable tests: they read like user stories.
  • Autocomplete: type tasksPage. and the editor lists every action.
  • Encapsulation: private selectors can't leak into tests.

8. Watch out for

  • "God" classes with 50 methods: split into components.
  • Deep inheritance (BasePage → FormPage → ...): prefer composition.
  • Boilerplate: beforeEach + new in every spec. Fixtures can create objects for you.
  • Detached methods lose this.

Rule of thumb: the page object knows HOW to use the page; the test knows WHAT should happen.
