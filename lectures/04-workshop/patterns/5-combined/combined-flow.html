Combined Flow fixtures set the stage; POM, factories and helpers act on it

  • 1. Fixtures build what the test asks for, dependencies first, and pause at use()
  • 2. A fixture can hand the test a POM object or a factory object
  • 3. The test body only calls objects, factories and helpers, and asserts
  • 4. After the test, fixtures tear down in reverse order
Why combine patterns? The basics in 2 minutes click or press I to show / hide

1. The idea in one sentence

Real suites don't pick one pattern. Each pattern does the job it is best at, and fixtures connect them.

Rule of thumb: fixtures decide WHAT a test starts with; page objects, factories and helpers decide HOW the test talks to the UI.

2. How it is wired

// fixtures/combined.fixture.ts
import { test as base } from '../../3-fixtures/fixtures';

export const test = base.extend<CombinedFixtures>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);  // POM
    await loginPage.navigate();
    await use(loginPage);
  },
  tasks: async ({ signedInPage }, use) => {
    await use(createTaskActions(signedInPage)); // factory
  },
});

3. Who does what

PatternJob in this suiteExample
Fixturessetup, sign-in, starting data, safety checks, cleanupsignedInPage, seed, failOnPageErrors
POMa stateful page with many locatorsloginPage.login(...), loginPage.errorMessage
Factory functionsgrouped actions with page remembered; test datatasks.deleteTask(...), buildTestUser({ password })
Helpersa one-off locator or actionwelcomeHeading(page)

4. When does each part run?

  1. Before the test: auto fixtures and the requested fixtures, dependencies first, each until its use().
  2. The test body: calls objects, factories and helpers.
  3. After the test: fixtures resume after use() in reverse order; page closes last.

5. Layers of fixture files

  • Folder 3 merges its fixture files into one test (mergeTests).
  • Folder 5 extends that test, because tasks needs signedInPage.
  • Specs import test from one file and never see the layers.

6. A typical real-world project

tests/
  fixtures/   auth.fixture.ts, api.fixture.ts, data.fixture.ts, index.ts
  pages/      LoginPage.ts, CheckoutPage.ts      (POM or factories, one per page)
  components/ Header.ts, DataTable.ts            (reused inside pages)
  helpers/    dates.ts, tables.ts                (small stateless functions)
  data/       users.ts, orders.ts                (test data factories)
  specs/      checkout.spec.ts ...               (scenario + assertions only)

7. Why combine?

  • Short tests: only the scenario and the assertions.
  • Fast, stable setup: sign-in and data without UI steps.
  • Automatic cleanup and safety checks.
  • Right tool per job instead of forcing one pattern everywhere.

8. Watch out for

  • Mixing without rules: agree as a team which pattern is for what.
  • Hiding the scenario in fixtures: if the test is about signing in, do it in the test body.
  • Too many auto fixtures: they cost time in every test.
  • Assertions in objects or helpers: keep expect in tests (setup checks in fixtures are fine).
