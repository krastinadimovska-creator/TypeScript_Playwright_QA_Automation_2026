  • 3. After the test, fixtures resume in reverse order (teardown)
  • 4. Worker fixtures survive across tests; test fixtures do not
What is a fixture? The basics in 2 minutes click or press I to show / hide

1. The idea in one sentence

A fixture is something a test needs, which Playwright prepares before the test and cleans up after it.

The test only asks for it by name in its arguments. It never builds it itself.

Analogy: in a restaurant the table is set before you sit down and cleared after you leave. You just say "a table for two, please".

2. You already use fixtures

Every { page } you have written is a built-in fixture:

test('opens home', async ({ page }) => {
  await page.goto('/');
});

Built-in ones: page, context, browser, request, browserName. You get a new, clean page for every test, and it is closed for you afterwards.

3. How a fixture works: setup, use, teardown

export const test = base.extend<{ todoPage: Page }>({
  todoPage: async ({ page }, use) => {
    // 1. SETUP: runs before the test
    await page.goto('/todos');

    await use(page);   // 2. the TEST runs here

    // 3. TEARDOWN: runs after the test,
    //    even if the test failed
  },
});

await use(value) is the line between "before" and "after". The value you pass is what the test receives.

4. When is a fixture called?

  • Only when needed: the test lists it, or another fixture it uses needs it. Unused fixtures are never run.
  • Once per test: if two fixtures both ask for page, they get the same page.
  • Dependencies first: page is ready before the fixtures that need it.
  • Teardown in reverse order, and always, also after a failure.
  • Auto fixtures run for every test, even if no test asks for them.
  • Worker fixtures run once per worker process and are shared by its tests (for slow, expensive setup).

6. Why not just beforeEach?

  • Setup and cleanup sit together in one function, so you can't forget the cleanup.
  • On demand: a test pays only for what it asks for.
  • Reusable across many spec files; just import test.
  • Typed: autocomplete shows what is available.
  • Isolated: every test gets its own copy, so tests can run in parallel.

7. When NOT to use a fixture

  • For a UI step the test performs, like "add a task" or "fill the form": use a helper function or a page object.
  • For the checks the test is about: keep those expects in the test, where readers look for them.
  • For a value used by one test only: a local variable is simpler.

Rule of thumb: fixtures prepare and clean up; the test acts and checks.
