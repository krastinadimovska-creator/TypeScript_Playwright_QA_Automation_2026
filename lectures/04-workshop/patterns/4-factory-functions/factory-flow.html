Factory Flow how a factory function builds actions and data, and what its closure remembers

  • 1. A factory is a plain function: call it, get an object back (no class, no new)
  • 2. The returned functions remember page and the private locators (a closure)
  • 3. Every call creates a new, separate object and closure
  • 4. Data factories: defaults + overrides, a fresh object every time
What is a factory function? The basics in 2 minutes click or press I to show / hide

1. The idea in one sentence

A factory function is a normal function that builds and returns something new: an object of actions, a single function, or a test data object.

No class, no constructor, no new, no this. You just call it.

Analogy: a coffee machine. You press a button (call the function) and get a fresh cup (a new object) every time. Choose options if you want: "with milk" = overrides.

2. The secret ingredient: a closure

A function remembers the variables that existed where it was created, even after the outer function has returned.

function createCounter() {
  let count = 0;              // private: not on the object
  return { next: () => ++count };
}
const counter = createCounter(); // createCounter has finished
counter.next(); // 1  ← `count` still lives on
counter.next(); // 2

In our tests the remembered variable is page (plus private locators), so you pass page once.

3. The same action in three patterns

PatternCreate onceCallHow the action finds page
Functional helpernothing to createawait addTask(page, 'Buy milk')passed as an argument in every call

Factory functionconst tasks = createTaskActions(page)await tasks.addTask('Buy milk')the closure: always the page given to the factory

4. When is a factory called?

  • Once per test, usually in beforeEach, or inside a fixture (folder 5: use(createTaskActions(signedInPage))).
  • Every call is new: new object, new closure. Tests never share state, so they can run in parallel.
  • Creating it is cheap and does nothing in the browser. Locators are lazy: they are only looked up when an action or expect uses them.
  • Data factories (buildTestUser()) are called right where the test needs the data.

5. Two kinds of factories in this folder

// Action factory: page in, actions out
const login = createLoginActions(page);
await login.loginAs(user);

// Data factory: defaults + overrides
const user = buildTestUser();
const bad  = buildTestUser({ password: 'wrong' });

7. Why use a factory?

  • Less code than a class: no constructor, no this.
  • page once: captured in the closure, not repeated in every call.
  • Real privacy: anything not returned can't be reached from the test.
  • Safe destructuring: const { addTask } = tasks still works.
  • Types for free: type TaskActions = ReturnType<typeof createTaskActions>.

8. Watch out for

  • Huge factories: 15+ methods is a "god object". Split by page or component.
  • OOP-heavy teams may find classes more familiar.
  • New functions per call: irrelevant in tests, but good to know.
  • Setup and cleanup (login, creating data through the API, deleting it) belong in fixtures; a factory has no teardown.

Rule of thumb: the factory builds the tools; the test uses them and checks the result.
